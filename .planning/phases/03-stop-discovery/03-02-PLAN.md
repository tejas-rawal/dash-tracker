## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04 | Tampering | StopController.getNearbyStops (`lat`, `lng`, `radius`, `count` query params) | high | mitigate | All four params are parsed via strict local helpers (`parseCoordinateParam`, `parsePositiveFloatParam`, `parseCountParam`) that reject `NaN`, `Infinity`, and non-finite values outright (`Number.isFinite`/`Number.isInteger` guards); `lat` is constrained to [-90,90], `lng` to [-180,180], `radius` must be a positive finite number, `count` must be a positive integer. Any failure returns 400 before the request reaches `StopService`, mirroring `PredictionController`'s `parseNumberParam` pattern (Task 1). |
| T-03-05 | Denial of Service | StopService.getNearbyStops (distance computed for every repository stop, then filtered/sorted/sliced) | medium | mitigate | Distance is computed once per stop against the already-in-memory, fixed-size stop list (bounded by the single agency's total stop count — no new upstream call, no unbounded loop). The response returned to the client is hard-capped at 50 results (D-07) regardless of the requested `count` or `radius`, so an overly broad query cannot produce an unbounded response payload (Task 1's `MAX_COUNT` clamp, Task 2's boundary tests). |
| T-03-06 | Information Disclosure | StopController error response body (`details` field) | low | accept | Malformed-parameter error messages name which parameter failed (e.g. "lat parameter must be a valid latitude") without echoing the full raw query string — consistent with existing `PredictionController` error bodies; no new sensitive-data exposure. |
</threat_model>
