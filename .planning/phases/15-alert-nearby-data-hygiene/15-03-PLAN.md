<objective>
Close review CR-01, which is also plan 15-01 assumption A1 and 15-UAT test 1. The developer chose to **reject** the current behavior, so this gap is closed in this phase. The decision is recorded as **D-16** in 15-CONTEXT.md.

**The gap:** some DASH alerts are structurally malformed:
- an `activePeriods` element that is `null`, `{}` or a number;
- an `activePeriods` value that is not an array, such as a string or a lone object;
- `informedEntities` of `[null]` or `{}`.

Any of these makes `ServiceAlertService.fetchAlerts()` reject with a TypeError. `ServiceAlertPollService` then logs an error and skips `applyAlerts`, so the previous snapshot keeps serving riders. That snapshot can include alerts DASH has since soft-deleted (ALRT-12). D-01's rationale ("one bad record must not freeze every update") applies just as well here.

**The fix (D-16):**
- Type both upstream lists as `unknown` on `DashAlertEntity`, so the compiler forces a check before use.
- Check each undeleted alert in one new `parseAlert` step, in this order: the `activePeriods` list, the `informedEntities` list, then the existing date validation (D-02/D-03).
- Drop a failing alert with one message-only warn naming its id and the malformed part. Every other alert in the poll is still applied.
- Inside well-formed informed entities, keep only string ids, so `null` no longer leaks into `informedRouteIds: string[]`.

Purpose:
- ROADMAP SC1 / ALRT-12: an alert DASH deleted is no longer kept on screen by a poll that one structurally broken alert would otherwise fail.
- ROADMAP SC2 / ALRT-13: an alert whose `activePeriods` cannot be trusted at all (not just its date values) is excluded and logged with its id.
- SC4: well-formed alerts and the existing malformed-date warns are unchanged.

Output:
- `src/server/api/models/ServiceAlert.ts`: `activePeriods?: unknown`, `informedEntities?: unknown`, and `DashInformedEntity` ids typed `unknown`.
- `src/server/api/services/ServiceAlertService.ts`: `isPlainRecord`, `readRecordList` and `parseAlert`; `fetchAlerts` warns with `parseAlert`'s malformed part.
- Tests: a real-poll E2E in `alertHygiene.test.ts` and a `structurally malformed alerts (D-16)` unit table in `ServiceAlertService.test.ts`.

Decisions honored:
- D-16 (new, implemented in full).
- D-01 to D-04 (per-alert drop and warn shape, extended to lists; the date warn text is unchanged).
- D-05 (ingestion only; `ServiceAlert` unchanged).
- D-06 (repository and poll untouched).
- D-07 (missing id still fails the poll).
- D-10 (deleted check first).

Claude's-discretion choices:
- **Structure.** `parseAlert(entity)` returns `{ alert }` or `{ malformed }`, so the `fetchAlerts` loop has one warn site whose wording covers both dates and lists. The list check, `findMalformedBound` and `mapToServiceAlert` take the checked lists as parameters, so TypeScript proves no code reads an unchecked list.
- **Arrays are not records.** `isPlainRecord` rejects arrays. Otherwise a nested list would pass as a period with no bounds, which reads as always active. This is the fail-safe direction.
- **Empty-string ids.** An empty-string `routeId`/`stopId` is still kept (A2 below). D-16 only requires that ids are strings, and an empty id cannot match a real route or stop.
- **Supersedes a 15-01 key link.** 15-01's key link `findMalformedBound(entity.activePeriods)` is replaced by `parseAlert(entity)`, which calls `findMalformedBound(periods)` (truth 12).

Spec-less probe fallback (no SPEC.md): the must_haves come straight from CR-01's reproduction table (15-VERIFICATION.md) and D-16. These edges are left open on purpose and recorded as assumptions:
- **A1:** a non-object *entity* (for example `null` in the entities array) is not covered by D-16. It still fails the whole poll under D-07, unchanged.
- **A2:** an empty-string `routeId`/`stopId` is kept as an id.
- **A3:** a very large `activePeriods` array still goes through `Math.min(...)`/`Math.max(...)` spreads in `deriveActiveWindow`. This is unchanged from 15-01 and covered by T-15-07 (accepted).
