<objective>
Browser code on an allowed origin can read API responses, and nothing else changes. The plan has two parts:
- Extract `createApp()` so the server and every route test share one wiring (D-12, a behavior-neutral commit first).
- Mount the established `cors` package app-level, right after `trust proxy`, with an exact allowlist from a new Zod-validated `CORS_ALLOWED_ORIGINS` (D-13, D-15). `Retry-After` and the rate-limit headers are exposed, allowed preflights are answered before any router, and requests without an allowed `Origin` are untouched.
Malformed origins stop the server at startup (D-15).

Purpose: CORS-01 and CORS-04, plus the mount that CORS-02 and CORS-03 rest on. Plan 18-06 proves the full response matrix of D-14. Per D-01, this runs after the whole toolchain, so it is written on TypeScript 6 in Biome 2 style.
Output: `createApp.ts`, `api/middleware/cors.ts`, `CORS_ALLOWED_ORIGINS` with tests, the `.env.example` entry, and docs.

Planning-time facts (verified 2026-11-10 against this checkout and the cors 2.8.6 tarball; do not re-derive):
- Versions: cors 2.8.6 (published 2026-01-22; dependencies object-assign 4.1.1 from 2017 and vary 1.1.2 from 2017; no lifecycle script) and @types/cors 2.8.19 (2025-06-07). Both rate OK in the legitimacy seam and clear the 7-day gate.
- How cors 2.8.6 handles origins (`lib/index.js`):
  - When `origin` is an array, it calls its header writer for every request. That adds `Vary: Origin` and `Access-Control-Expose-Headers` even to requests without an `Origin`, sends no `Access-Control-Allow-Origin` for an unlisted origin, and answers every OPTIONS itself with 204.
  - When `origin` is a callback that answers `false`, the middleware calls `next()` without touching the response.
  - When the callback answers a string, it sends `Access-Control-Allow-Origin` with that exact string plus `Vary: Origin`. It then answers OPTIONS with 204 (`optionsSuccessStatus`), with `Access-Control-Allow-Methods` at the library default, `Access-Control-Allow-Headers` echoing `Access-Control-Request-Headers`, and the exposed headers. Any other method goes on to `next()`.
- Behavior without CORS today:
  - `OPTIONS /api/v1/predictions` answers 200 with body `GET,HEAD` and `Allow: GET,HEAD` from Express's automatic OPTIONS handling, and never runs the rate limiter, because the route is GET-only.
  - `OPTIONS /api/v1/favorites` without `X-Device-Id` answers 400 from `requireDeviceId`.
  - `GET /api/v1/no-such` answers Express's default 404.
  CORS-04 requires all three to stay exactly like this for requests without an `Origin`.
- `upstreamRateLimiter` uses `standardHeaders: "draft-8"`, so limited routes send `RateLimit` and `RateLimit-Policy`. That is D-13's condition for exposing them alongside `Retry-After`.
- The `src/test/app.ts` default export is imported by 15 route test files (`alertHygiene`, `busRoutes`, `dataBootRetry`, `dataNotReady`, `dataReload`, `dataReloadStream`, `favoriteRoutes`, `healthRoutes`, `predictionRoutes`, `rateLimit`, `recentRoutes`, `stopRoutes`, `streamCap`, `trustProxy`, `upstreamTimeout`). D-12 keeps that file and makes it call `createApp()`, so none of those files change.
- `vitest.config.mts` excludes `src/app.ts` and `src/config/**` from coverage, but not `src/createApp.ts` or `src/api/middleware/cors.ts`. Both run in every route test.
- `environment.ts` throws `Invalid environment configuration:` followed by one `  <path>: <message>` line per Zod issue at import time. `app.ts` imports config before anything else, so an invalid value stops the process before it listens.
