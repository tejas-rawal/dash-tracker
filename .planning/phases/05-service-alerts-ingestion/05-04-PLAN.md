<objective>
Close the confirmed WR-01 defect from 05-REVIEW.md, promoted to a blocking gap in 05-VERIFICATION.md (`gaps[0]`, Truth 5, `05-VERIFICATION.md:16-27,58-60`): the body-shape guard in `ServiceAlertService.ts`'s `fetchFromDashApi()` is `body === null || typeof body !== "object"`. Because `typeof [] === "object"` in JavaScript, an array-rooted `response.data` (or a JSON string that parses to one) silently passes this guard, gets cast to `DashAlertsApiResponse`, and `fetchAlerts()` then reads `.entities` on an array — always `undefined` — logging "No service alerts found" and resolving to `[]` instead of throwing `UpstreamApiError`. This directly contradicts 05-03-PLAN.md's own written STRIDE claim that "a string that parses to a non-object JSON value (array-at-root, primitive, or invalid JSON) still throws `UpstreamApiError` exactly as before" — that claim is false for the array-at-root case today.

This plan adds `Array.isArray(body)` to the guard condition and locks the fix in with two regression tests (array literal body, and JSON-string body that parses to an array), while proving every pre-existing guard/mapping test from 05-01/05-02/05-03 still passes unmodified.

Purpose: ALRT-01 requires the fetch pipeline to fail loud on a malformed upstream response rather than silently degrading to "zero alerts" — an availability/integrity failure that would be indistinguishable from "no active alerts" to any downstream consumer (Phase 6). This is the last confirmed code defect blocking Phase 5's verification from `gaps_found` to `passed`.

Output: `ServiceAlertService.ts`'s body-shape guard rejects an array-rooted body in both its pre-parse (already-an-array `response.data`) and post-parse (JSON-string-that-parses-to-an-array) forms, proven by new passing tests, with zero regression in the existing 34 phase-scoped tests.
</objective>
