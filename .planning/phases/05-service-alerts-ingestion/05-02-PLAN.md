Close UAT gap G-05-1: the real DASH/Swiftly API returns 404 for the service-alerts poll because `ServiceAlertService.buildDashApiUrl()` builds the wrong endpoint path. The correct path — `/real-time/{agency}/gtfs-rt-alerts/v2` — was CONFIRMED by the user directly from Swiftly's own API reference docs (see `.planning/debug/service-alerts-404.md`; this is settled, not re-diagnosed here).

This plan: (1) fixes the path and its test/documentation traces, (2) fixes a correctness bug in `deriveActiveWindow` (WR-03 from `05-REVIEW.md`) that silently collapses an open-ended active window to a bounded one whenever the same alert's `active_period` array mixes bounded and open-ended entries, and (3) adds defensive response-shape validation (WR-01/WR-02) so a non-object response body or a malformed entity item fails loud via `UpstreamApiError` instead of a low-signal `TypeError` or a silently-empty alert list — a real risk now that this plan makes the poll hit a live, previously-unreachable endpoint whose exact JSON-vs-protobuf response behavior was never independently confirmed during diagnosis.

Purpose: ALRT-01..04 require a working, non-erroring fetch -> normalize -> filter-by-active-window -> query pipeline against the REAL DASH/Swiftly API, not just against mocked tests. The original 05-01-PLAN.md shipped a fully-tested pipeline that 404'd the moment it touched the live API — this plan is what makes that pipeline actually reach the real service alerts.

Output: `ServiceAlertService.ts` fetching the correct, confirmed endpoint with hardened response-shape validation and a corrected active-window collapse; updated tests locking in all three fixes; `05-01-PLAN.md`'s stale wrong-path text corrected so it no longer contradicts the shipped implementation.

    Per `05-REVIEW.md` WR-01: in `fetchFromDashApi()`, immediately after `const response = await axios.get(url);` and before the `return response.data as DashAlertsApiResponse;` line, add a guard that throws `new UpstreamApiError("DASH API returned a malformed service alerts response (body is not an object)")` when `response.data` is `null` or `typeof response.data !== "object"`. This converts what would otherwise be an unhandled generic `TypeError` (e.g. from a misparsed protobuf-binary body) into the same descriptive, `ServiceAlertPollService`-caught error type the sibling entity-shape checks already produce.
