<objective>
Build the server-side ingestion pipeline for GTFS-RT service alerts: fetch from the DASH/Swiftly service-alerts endpoint on a dedicated ~5-minute boot-triggered poll, normalize each alert into a `ServiceAlert` domain model (D-01 through D-07 in `05-CONTEXT.md`), and expose an in-memory, currently-active-only query surface (`ServiceAlertRepository.getActiveAlerts()`) ready for Phase 6 to consume. No client-facing HTTP surface is added — this phase is ingestion only.

Purpose: ALRT-01..04 require a working fetch -> normalize -> filter-by-active-window -> query pipeline that runs independently of the existing 30s prediction poll and never blocks server startup, so Phase 6 has a stable, queryable alert store to embed into route/stop/prediction responses.

Output: `ServiceAlert` model, `ServiceAlertService` (fetch + Dash-to-domain mapping), `ServiceAlertRepository` (singleton in-memory store + active-window query), `ServiceAlertPollService` (boot-triggered 5-minute interval driver), wired into `app.ts` non-blocking.

<assumption_delta_decision>
decision: no-change
rationale: The deterministic scanner's "second" trigger matched "...the existing 30-second prediction poll" in the ROADMAP goal line — a time-unit word ("30-second"), not a pluralization of an identity/platform/tenant/source-of-truth concept. Confirmed against CONTEXT.md D-01: `ServiceAlertPollService` is a wholly new, independent interval loop — not a second instance of `PredictionStreamService`'s abstraction (different trigger model: boot-triggered vs. per-stop-subscription-triggered; different cadence: 5min vs. 30s; different upstream data source; no shared state). No assumption delta to record.
</assumption_delta_decision>

<flagged_assumptions>
Per the spec-less probe fallback (no SPEC.md exists for this phase), every edge-probe row the deterministic engine could not auto-classify is recorded here as an explicit decision, plus the two external-API-shape unknowns CONTEXT.md flagged as unconfirmed:

1. **(ALRT-01, concurrency)** No explicit poll-overlap guard exists on `ServiceAlertPollService` — each `setInterval` tick fires an independent `void pollAlerts()` call (mirrors `PredictionStreamService.poll()`, which also has no overlap guard). At a 5-minute interval this is not expected to overlap DASH API latency in practice; if it did, `ServiceAlertRepository.applyAlerts()`'s full-Map-replacement means the last-completing fetch wins with no torn/partial state — never a crash, only "last write wins" ordering.
2. **(ALRT-02, adjacency)** `activePeriod` boundaries are inclusive on both ends — an alert is active when `start <= now <= end`. An alert becomes inactive the instant `now > end`, not before; it becomes active the instant `now >= start`.
3. **(ALRT-02, empty)** Zero `active_period` entries -> open-ended/always-active window (`{start: null, end: null}`, per D-03). Zero alert entities in the API response -> empty `ServiceAlert[]`/store, not an error (mirrors `BusDataRepository`'s `!routes` -> empty-map handling). Zero currently-active alerts in the store -> `getActiveAlerts()` returns `[]`, not an exception.
4. **(ALRT-02, ordering)** `getActiveAlerts()` returns alerts in `Map` insertion order (the order the DASH API returned them in that fetch), matching the existing `Array.from(this.X.values())` convention in `BusDataRepository.getAllRoutes()`/`getAllStops()`. No secondary sort is applied.
5. **(ALRT-03, unclassified — informed_entity handling)** An alert with no `informed_entity` entries (a system-wide/global alert per the GTFS-RT spec) is still ingested and stored with `informedRouteIds: []`/`informedStopIds: []` — it is never dropped. Deciding how a globally-scoped alert should be matched against a specific route/stop is explicitly Phase 6's job (ALRT-05..09), not this phase's.
6. **(ALRT-04, unclassified — filter timing)** Active-window filtering happens at QUERY time (`getActiveAlerts(referenceTime)` evaluated against the current wall clock on every call), not at fetch/store time. The repository stores every fetched alert (past, current, and future) as-is; only the read path filters. This avoids a not-yet-active alert sitting unfiltered for up to 5 minutes past when it should have become active.
7. **(external API shape)** The DASH/Swiftly service-alerts endpoint path is ASSUMED as `/real-time/{agency}/service-alerts` — not yet documented in `.planning/codebase/INTEGRATIONS.md`, and could not be confirmed against live Swiftly API docs during planning (publicly reachable doc URLs returned 404s). `DashAlert`/`DashAlertEntity`/`DashAlertsApiResponse` field casing is ASSUMED to follow the standard GTFS-RT JSON encoding (snake_case: `active_period`, `informed_entity`, `header_text`, `route_id`, `stop_id`) since GTFS-RT is a standardized wire format, distinct from DASH's other custom `{success, data}`-wrapped REST endpoints. If the live response differs, only `ServiceAlert.ts`'s `Dash*` interfaces and `ServiceAlertService.ts`'s `buildDashApiUrl()`/`mapToServiceAlert()` need adjusting — the model/repository/service architecture and every requirement above are unaffected.
</flagged_assumptions>
