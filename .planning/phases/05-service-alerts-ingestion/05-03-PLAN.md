<objective>
Close UAT gap G-05-2: after 05-02 fixed the endpoint 404 (G-05-1), booting against the LIVE DASH/Swiftly API now fails with `error: Failed to poll service alerts: DASH API returned a malformed service alerts response (body is not an object)`. Full root-cause diagnosis: `.planning/debug/service-alerts-malformed-body.md`.

Two independent, confirmed bugs, both in `ServiceAlertService.ts`/`ServiceAlert.ts`:

1. `fetchFromDashApi()` only accepts an already-parsed object `response.data`. It has no fallback for a JSON-encoded string body, which is what axios's default transform produces when the upstream `Content-Type` isn't recognized as JSON — this is the proximate cause of the observed error.
2. `DashAlertsApiResponse`/`fetchAlerts()` read the top-level field as `entity` (singular, GTFS-RT protobuf-JSON convention), but the live DASH/Swiftly payload uses `entities` (plural). This alone doesn't throw (`response.entity === undefined` early-returns `[]` with a warn log) but silently and permanently discards every real alert — a live-breaking bug independent of bug 1.

This plan: (1) adds a `JSON.parse` fallback in `fetchFromDashApi()` for a string `response.data`, only throwing `UpstreamApiError` if that parse also fails or the parsed result isn't a non-null object, and (2) renames `entity` -> `entities` in `DashAlertsApiResponse` and every read site in `fetchAlerts()`, matching the confirmed live API shape.

Purpose: ALRT-01..04 require a working fetch -> normalize -> filter pipeline against the REAL DASH/Swiftly API. 05-02 fixed the endpoint path but the pipeline still cannot ingest a single real alert — this plan is what makes it actually work end-to-end against production.

Output: `ServiceAlertService.ts`/`ServiceAlert.ts` correctly parsing a string-encoded response body and reading the live `entities` field; tests locking in both fixes while preserving the existing WR-01/WR-02 guard coverage from 05-02 (updated to the renamed field).
</objective>
