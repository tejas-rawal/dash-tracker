<objective>
Close the SSE half of v0.2 WR-05 (ERR-01). Today `PredictionStreamController` has no `error` listener on the SSE response. An `error` emitted there, for example a write to a broken mobile socket (EPIPE/ECONNRESET), has no handler, so Node treats it as an uncaught exception, and the subscriber's 30 s DASH poll can keep running for a dead client.

After this plan:
- `res.on("error")` logs at warn with the stop id and message (D-13).
- It runs exactly the disconnect cleanup, `unsubscribe()` then `res.end()`, through one shared, idempotent cleanup function that `req.on("close")` also uses (D-14).
- The listener is attached before `subscribe` is awaited, so errors before or around `writeHead` are covered.
- `PredictionStreamService` is untouched (D-15). Its idempotent `unsubscribeFrom` already stops the per-stop poll when the last subscriber leaves, and other subscribers keep receiving updates.

Purpose: ROADMAP Phase 12 success criterion 4.
Output: the updated controller and its test file, including a multi-subscriber integration test against the real `PredictionStreamService`.

Prohibition probe (spec-less fallback, stage 2): every raw must-NOT candidate for ERR-01 was routine engineering and is owned by the truths above (double cleanup, leaked interval, crash on unhandled `error`), so zero prohibitions are kept for this requirement. <flagged_assumptions>
The edge probe returned ERR-01 as `unclassified`. Per the spec-less fallback rules it stays **unresolved** (not auto-resolved) and is surfaced here for review. The planner's working assumptions:
1. A second `error` event on the same response logs a second warn line but never re-runs cleanup. Idempotency is guarded by a flag, not by removing listeners.
2. A response `error` or request `close` after `subscribe` rejected (the 404/502 path) only records the finished flag. No subscription exists to remove, and no `res.end()` is issued by cleanup.
3. D-15 relies on Node emitting `error` on the `ServerResponse` for a failed write to a broken socket. If a given failure only produces `close`, the existing close path still runs the same cleanup, so there is no leak either way.
4. `res.end()` on a response whose socket is already destroyed is a harmless no-op in Node 20. The pre-subscribe disconnect path now calls it too, where before it only unsubscribed.
</flagged_assumptions>

        const { initialPayload, unsubscribe } = subscription;

        if (closed || req.destroyed) {
            unsubscribe();
            return;

            logger.error(`Failed to write initial SSE frame for stop ${stop}: ${message}`);
            unsubscribe();
            return;
        }

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Rider client socket to SSE response | An untrusted, frequently-dropped mobile connection. Its errors surface asynchronously on the `ServerResponse`. |
| Per-stop poll to DASH upstream | Each live subscriber keeps a 30 s upstream poll alive, so a leaked subscriber costs upstream calls indefinitely. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-11 | Denial of service | `PredictionStreamController` SSE response | high | mitigate | `res.on("error")` is registered before `subscribe` is awaited. Without a listener, an `error` event throws and takes the whole server down for every rider. The tracer test and the pending-subscribe test cover it. |
| T-12-12 | Denial of service | Per-stop poll after a socket error (a leaked subscriber keeps a 30 s DASH poll alive) | medium | mitigate | The shared, idempotent cleanup calls `unsubscribe()`, and `unsubscribeFrom` clears the interval once the last subscriber leaves. The integration test proves no further upstream fetch occurs. |
| T-12-13 | Information disclosure | SSE warn log line | low | mitigate | Only the stop id and `error.message` are logged, never the error object, so no socket or request internals reach the log (D-13). |
| T-12-14 | Denial of service | Log volume from routine client aborts | low | accept | One warn line per broken connection, bounded by the connection count. Warn level (D-13) keeps these out of error alerting. |

No package installs in this plan.
</threat_model>
