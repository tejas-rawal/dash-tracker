<objective>
Stop one client IP from multiplying live DASH load by holding many prediction streams open (review WR-02 from Phase 14, deferred at UAT). Today the shared 60/min bucket counts a stream connect once and never looks at it again, so one IP can open 60 streams a minute and keep them all open, each driving a 30 s DASH poll. This plan adds a per-IP cap of 5 concurrent open streams on `GET /api/v1/predictions/stream` only.

Purpose (ROADMAP Phase 16 success criteria):
- SC1: an IP holding the maximum gets 429 `{ error, details }` on its next stream connect, while another IP can still open streams.
- SC2: closing a stream (client disconnect, server end, socket error) frees its slot right away, with no window to wait for.
- SC3: open streams are never closed or written to by the cap, and the 60/min bucket keeps counting stream connects as before.

Output:
- New middleware `src/server/api/middleware/streamConcurrencyCap.ts` (`createStreamConcurrencyCap`, shared `streamConcurrencyCap`), wired after `upstreamRateLimiter` on `/stream` in `predictionRoutes.ts`.
- New test client helper `src/server/test/streamClient.ts`.
- Real-app tests in `src/server/api/routes/streamCap.test.ts`, middleware tests in `src/server/api/middleware/streamConcurrencyCap.test.ts`.
- The "Rate limiting" bullet in `.claude/CLAUDE.md` and `AGENTS.md` mentions the cap.

Decisions honored: D-01 (cap 5), D-02 (every connection counts), D-03 (named constant), D-04 (synchronous claim), D-05 (cap before validation, release on every path), D-06 (once-only release, no negative counts, delete at 0), D-07 (bucket first), D-08 (never touches open streams), D-09 (bucket's client key), D-10 (distinct details), D-11 (fixed Retry-After), D-12 (warn per rejection, no query string), D-13 (separate middleware, factory, one shared instance, controller unchanged), D-14 (release on res 'close'), D-15 (hand-rolled map after a package check).

Pattern-mapper flags, resolved:
- **D-09 key.** Use `ipKeyGenerator(req.ip)`, exported by express-rate-limit 8.7.0. The bucket keeps the library's default key function, which returns `ipKeyGenerator(request.ip, 56)`, and `ipKeyGenerator`'s default subnet is also 56. The cap therefore keys exactly as the bucket does. Its warn shows `127.0.0.1` rather than `::ffff:127.0.0.1`, matching the bucket's warn, and one IPv6 client cannot rotate through addresses inside its /56 to get more slots. Probe on this machine: `::ffff:127.0.0.1` gives `127.0.0.1`; `2001:db8:abcd:1200::1` and `2001:db8:abcd:12ff::2` both give `2001:db8:abcd:1200::/56`; `2001:db8:abcd:1300::1` gives `2001:db8:abcd:1300::/56`.
- **`req.ip` can be undefined.** Express derives `req.ip` from the socket address, which disappears once the socket is gone. Such a request is still capped, under one shared key `UNKNOWN_CLIENT_KEY = "unknown"`, so no request path skips the cap (fail closed). Its 'close' still releases the slot. Separately (Task 2), a connect whose response is already closed (`res.destroyed`) is dropped without a claim and without `next()`. Its 'close' event has already fired, so a claim would never be released and would lock that IP out for good. Nobody is left to read a response.
- **Where SC3 is tested.** In both places, because they prove different things. (1) The real app (`streamCap.test.ts`): the cap's 429 carries the bucket's `RateLimit` header with `r` decremented, which proves the real `predictionRoutes.ts` order (D-07), and the open streams keep receiving poll frames at the cap (D-08). (2) A middleware chain (`createUpstreamRateLimiter()` then a fresh cap) with exact `r=` counts, plus "a bucket-rejected connect claims no slot". No fake DASH is needed: the real-app file mocks `PredictionService` the way `predictionRoutes.test.ts` does, so streams open without route data.

D-15 package check (2026-10-12): no well-maintained package fits better, so the counter is the hand-rolled `Map<string, number>`.
- express-rate-limit 8.7.0 (already a dependency) is window-only. Its store can decrement, but every count resets when the window expires, so streams still open at that point would be forgotten.
- rate-limiter-flexible has no concurrency mode. Its documented workaround (`duration: 0` plus `penalty`/`reward`) is promise-based and would add a dependency to replace about 15 lines.
- p-limit, p-queue and bottleneck limit in-process promise concurrency and queue work rather than rejecting per client key.

Claude's-discretion choices (CONTEXT):
- details text: "Too many open prediction streams from this client; close one before opening another" (the D-10 example). `Retry-After` is 5 s, held in the cap's own constant `STREAM_CAP_RETRY_AFTER_SECONDS`. It mirrors `errorResponse.ts`'s `RETRY_AFTER_SECONDS` but does not import or export it, because that constant and its comment belong to the 503.
- `RateLimit`/`RateLimit-Policy` headers stay as the bucket set them. The cap adds no rate headers.
- No accessor. The factory takes its count map as an optional parameter (`createStreamConcurrencyCap(openStreams = new Map())`), the way express-rate-limit takes a store. Production passes nothing and each instance owns a fresh map (D-13). Tests inject a map to read exact counts and to prove deletion at 0 (D-06), which HTTP alone cannot show.
- Tests: real sockets for streams through the shared `connectStream`/`openStream` helper. Waits use `vi.waitFor` on server-side state (the injected map, or `trackOpenResponses`) instead of fixed sleeps. Mock req/res are used only for dead connections, an undefined `req.ip`, repeated 'close' events and IPv6 key parity.

Reversibility: every decision here lives in one new middleware file plus one route line. It adds no stored data, no env var and no new response field (a 429 `{ error, details }` already exists on this route). All ratings are `reversible`, so no reversibility gate applies.
