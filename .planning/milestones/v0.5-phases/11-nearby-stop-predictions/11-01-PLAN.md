<objective>
Deliver the core of `GET /api/v1/predictions/nearby`: a rider sends `lat`/`lng` and gets live, nearest-first predictions for every stop around them, each with id/name/code, `distance` in miles, route-to-destination predictions in the existing `RoutePrediction`/`Destination` shapes, and embedded active alerts, plus a top-level `generatedAt`. All of it comes from exactly one uncached call to DASH/Swiftly `real-time/{agency}/predictions-near-location` (NEAR-01, NEAR-04..NEAR-07). Upstream failures return 502, and a malformed entry is dropped without failing the request (NEAR-09).

This plan also defines the full service contract, including `NearbyPredictionOptions { radius, number }`, meters conversion (D-10) and `number` forwarding (D-11), so the service-side halves of NEAR-02/NEAR-03 are done and unit-tested here. Plan 11-02 exposes `radius`/`number` over HTTP with their 400 caps and completes the NEAR-08 matrix.

Pattern-map decisions, resolved:
1. Empty-string lat/lng: the new controller has its own strict parsers that reject `""`, whitespace-only, repeated (array) and nested (object) values (D-12). `StopController` is not touched, so `/stops/nearby` keeps its current behavior, which CONTEXT marks "Unchanged". The helpers are deliberately not extracted into a shared module.
2. Network errors: only `NearbyPredictionService` wraps axios rejections as `UpstreamApiError` (502). `PredictionService`/`VehicleService` rejection behavior stays as it is.
3. Distance: `distanceToStop / 1609.344`, unrounded (D-17). The rounding great-circle helper in `./distance` is not reused.

Purpose: This is the milestone v0.5 capability. A rider gets "what's arriving around me" in one call.
Output: New `predictionMapping.ts`, `NearbyPredictionService.ts`, `NearbyPredictionController.ts`, nearby types in `Prediction.ts`, the `/nearby` route, and service, mapping and E2E route tests.
</objective>

<assumption_delta_decision>
Detector signal: kind `optional`, from "An optional `radius` (miles, default 0.5, capped)".
Primary noun: the rider's location (`lat`, `lng`). It stays required and is still the request's identity/anchor.
Decision: no-change. `radius` is a new optional tuning parameter on a brand-new endpoint, and it mirrors the optional `radius` (default 0.5 mi) that `/stops/nearby` already has. Nothing that used to be required became optional, and no derived value in an existing model became chosen, so there is nothing to promote.
Invariant test: omitting both `radius` and `number` still yields a valid response built from the defaults (`meters=805`, no `number`). Task 1's E2E happy-path test covers this.
</assumption_delta_decision>
