<objective>
Let the rider tune the search: `radius` (miles, default 0.5, max 1) and `number` (predictions per destination, 1..10) flow from the query string through the controller into the service's `meters`/`number` upstream params (NEAR-02, NEAR-03, D-10, D-11). Then close NEAR-08 with the full 400 matrix for `lat`/`lng`/`radius`/`number`: boundaries, blank values, repeated params, non-numeric values and validation order. Every 400 happens before any upstream call.

The service already implements the meters conversion (`Math.ceil(radius * 1609.344)`) and forwards `number` only when it is defined (Plan 11-01). This plan owns only the HTTP surface. Validation stays in `NearbyPredictionController`'s own strict parsers, and `StopController` is not touched, so `/stops/nearby` keeps its existing behavior (pattern-map decision 1, recorded in 11-01).

Assumption-delta (optional `radius`): no-change, recorded in 11-01's `assumption_delta_decision` block.

Purpose: Riders can widen or narrow the search and limit how many arrivals they see, and bad input fails fast with a clear 400 instead of producing a wrong-location query or an oversized upstream call.
Output: radius/number handling in `NearbyPredictionController.ts`, a new `NearbyPredictionController.test.ts`, and radius/number E2E cases in `predictionRoutes.test.ts`.
</objective>
