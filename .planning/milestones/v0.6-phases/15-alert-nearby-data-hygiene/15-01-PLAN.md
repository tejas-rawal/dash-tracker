<objective>
Stop two kinds of bad alert from reaching riders, and do it at the single point where alerts enter the system:
- **Soft-deleted alerts (ALRT-12):** DASH marks an alert deleted by setting `deletedAt` but keeps it in the feed. Today such an alert is still shown if its window covers now.
- **Malformed dates (ALRT-13, Phase 9 WR-02):** today one unparseable `activePeriods` date makes `deriveActiveWindow` throw `RangeError`, which fails the whole poll and freezes every alert update (including new deletions) until DASH fixes the record.

Purpose:
- ROADMAP SC1: a deleted alert never appears on route, stop, nearby-stop or nearby-prediction responses.
- ROADMAP SC2: a malformed-date alert is excluded from every response and logged with its id.
- ROADMAP SC4: well-formed alerts are served exactly as before.

Output:
- `DashAlertEntity.deletedAt?: unknown`; `DashActivePeriod.start/end` typed `unknown` (honest about upstream, narrowed by the validator).
- In `ServiceAlertService.fetchAlerts()`: a per-alert loop that drops deleted alerts silently, drops malformed-date alerts with one warn each, and maps the rest.
- Unit tests in `ServiceAlertService.test.ts` and a new fake-DASH E2E, `src/server/api/routes/alertHygiene.test.ts`.

Decisions honored: D-01 (per-alert drop), D-02 (whole alert on any bad period), D-03 (malformed definition), D-04 (one stateless warn naming id and bound), D-05 (ingestion only, no domain field), D-06 (repository untouched; service never emits an invalid bound), D-07 (missing id still fails the poll), D-08 (any non-null deletedAt), D-09 (deleted drops are silent), D-10 (deleted check first).

Claude's-discretion choices (CONTEXT):
- Structure: three small helpers inside `createServiceAlertService` next to the existing `isValidDashAlertEntity` (file-local consistency): `isDeleted`, `isParseableDate`, `findMalformedBound`. `fetchAlerts` runs one `for...of` loop so the D-10 order reads top to bottom.
- `deriveActiveWindow` takes pre-validated periods and filters bounds with `isParseableDate`, which also narrows `unknown` to `string`.
- Warn wording: `Dropping service alert ${entity.id} with a malformed activePeriods ${malformedBound} date` (VehicleService "Dropping vehicle X ..." voice; message-only per Phase 12 D-06/D-12).
- Widen `DashActivePeriod` bounds to `unknown` instead of casting in tests (PATTERNS option 1), matching D-08's "honest type" for `deletedAt`.

Spec-less probe fallback (no SPEC.md):
- Edges: the ALRT-12 and ALRT-13 rows came back `unclassified`. CONTEXT D-02/D-03/D-08/D-09/D-10 answer them, so both are resolved explicit as labeled truths. The sub-edges no decision covers are listed below as flagged assumptions, not dropped.
- Prohibitions:
  - Recall surfaced: exposing deletion metadata publicly or in logs; guessing/repairing a broken window; over-filtering live alerts; noisy logs for routine deletions; one bad alert freezing every update; logging raw upstream values; log injection through upstream ids.
  - Kept (bespoke values items): no deletion metadata exposure; no guessed or repaired windows.
  - Dropped as routine/owned elsewhere: over-filtering and freezing updates are pinned as truths (D-08, D-01); deletion log noise is D-09; raw-value logging is the D-04 truth.
  - Canon: log injection through upstream id strings (CWE-117) is canon; covered by /gsd-secure-phase, not minted here.

Flagged assumptions (surfaced, not resolved by any decision):
- A1: an `activePeriods` value that is not an array, or a period element that is not an object (for example `null`), is a structural break outside D-02/D-03. Its behavior is unchanged: it throws and the poll keeps the previous set, the same outcome D-07 keeps for a missing id. Confirm, or schedule per-alert dropping for it too.
- A2: an inverted window (start later than end) is not malformed under D-03 and is kept as-is; it simply never matches `isAlertActive`.
- A3: when several bounds in one alert are bad, the single warn (D-04) names the first one found, scanning periods in order and `start` before `end`.
</objective>
