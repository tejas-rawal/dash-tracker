<objective>
Bound every DASH call made through the shared axios client and turn every transport failure into `UpstreamApiError`, so a hung, slow or failing DASH produces a 502 instead of a pending request or a 500.

1. `DASH_API_TIMEOUT_MS` (Zod-validated, default 10000 ms) becomes `environment.dashApi.timeoutMs` (D-02, D-03).
2. A request interceptor on `axiosInstance` gives each request its own `AbortSignal.timeout(timeoutMs)`. This is a hard total deadline, not axios's socket-idle `timeout`, and it covers every DASH call, including the bulk routes load (D-01, D-04).
3. A response-error interceptor maps timeouts, aborts, connection errors and non-2xx responses to a message-only `UpstreamApiError`. Timeouts read `DASH API request timed out after {timeoutMs}ms`, and everything else reads `DASH API request failed: {message}` (D-05, D-06, D-08). The existing controller mapping turns these into 502 with no controller edits (D-09).

The tracer proves the whole path on `GET /api/v1/vehicles` against a real local server that accepts connections and never answers. Task 2 pins the edge cases at the client (slow trickle, fresh deadline per call, refused connection, 503, no key or URL leak) and the env validation.

Purpose: UPST-01 and UPST-02, success criteria 1 and 2. This closes the v0.5 WR-02 / T-11-06 "shared axios client has no timeout" concern.
Output: bounded, error-mapped `src/server/config/axios.ts`; `DASH_API_TIMEOUT_MS` in `environment.ts`, `setup.ts` and `.env.example`; three new test files.

Prohibition probe (spec-less fallback): two bespoke prohibitions were kept, transparency (no 2xx fallback on failure) and rider-location privacy (no URL in error text). `DASH_API_KEY` leakage is canon (OWASP sensitive-data exposure), so it is covered by /gsd-secure-phase and threat T-12-01 rather than minted as a prohibition.

Plan 12-02 (wave 2) builds on this. It removes Nearby's now-redundant wrap (D-07) and extends the blackholed-DASH E2E to `/predictions`, `/predictions/nearby`, the startup load and the alert poll.
</objective>

axios 1.7.9 facts (verified in node_modules, standing in for the disabled research step, D-04):
- `lib/adapters/http.js:217-227`: when `config.signal` aborts, `abort(reason)` emits `new CanceledError(null, config, req)` (message "canceled", code `ERR_CANCELED`) because the listener receives an Event (`reason.type`). `emitter.once('abort', reject)` rejects the whole request, including mid-body (lines 603-614 destroy the response stream).
- `lib/adapters/http.js:650`: axios's own `timeout` option is `req.setTimeout`, a socket-inactivity timer. A trickle of bytes resets it, so it is not a hard deadline.
- `axios.isCancel(error)` is true for that CanceledError. Response-error interceptors receive adapter rejections.
- Only on rejection does the adapter remove its signal listener. After a successful response the listener stays until the signal fires, and that abort is then a no-op on the finished request. This is accepted as T-12-06.
- Node 20's `http.globalAgent` keeps sockets alive, so test servers must call `server.closeAllConnections()` before `close()`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DASH upstream to API server | An untrusted network peer that can hang, trickle bytes, refuse connections or return 5xx. Its failure must stay bounded and contained. |
| API server to rider client | 502 response bodies echo `UpstreamApiError.message` (`details`), so anything in that message reaches the client. |
| Process environment to config | `DASH_API_TIMEOUT_MS` is operator-supplied and validated at startup. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-01 | Information disclosure | `toUpstreamApiError` / response-error interceptor in `src/server/config/axios.ts` | high | mitigate | An `UpstreamApiError` is built from a message string only. The axios error, which holds `config.headers.Authorization` = `DASH_API_KEY`, is never passed, attached or spread (D-06). axios.test.ts asserts there is no config/request/response/cause property and no key in the message or `util.inspect`. The route E2E asserts no key in the 502 body or in any log call. |
| T-12-02 | Denial of service | Shared axios client (every DASH call) | high | mitigate | A request interceptor sets `AbortSignal.timeout(timeoutMs)` on every request as a hard total deadline (D-04). The slow-trickle test proves a byte every 50 ms cannot hold a request open past it. |
| T-12-03 | Information disclosure | `UpstreamApiError` message, from the nearby request URL, which carries rider lat/lng | medium | mitigate | The message is built from axios's `error.message` (no path or query) or the fixed timeout text. axios.test.ts asserts that a nearby-shaped request's wrapped error never contains the coordinates or the path. |
| T-12-04 | Tampering | `DASH_API_TIMEOUT_MS` env value | low | mitigate | `z.coerce.number().int().positive()` rejects 0, negatives, fractions, NaN and empty values at startup, so the deadline can never be disabled by a bad value. environment.test.ts covers each case. |
| T-12-05 | Denial of service | Deadline signal lifetime (single-signal pitfall) | medium | mitigate | The signal is created inside the request interceptor for each call, never on `axios.create` or on the instance defaults. The consecutive-call test proves a later call after an elapsed window, and after a timed-out call, still succeeds. |
| T-12-06 | Denial of service | axios 1.7.9 keeps a successful request's abort listener until its deadline fires | low | accept | Retention is bounded by `timeoutMs` (10 s by default). The `AbortSignal.timeout` timer is unref'd, and the late abort is a no-op on a finished request. `AbortSignal.timeout` has no cancel handle, and replacing it with a manual controller would add code without a measurable benefit at this traffic level. |

No package installs in this plan (axios and zod are existing dependencies), so there is no supply-chain threat row.
