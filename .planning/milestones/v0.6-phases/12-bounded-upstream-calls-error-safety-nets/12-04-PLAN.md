<objective>
Close the process half of v0.2 WR-05 (ERR-02). The process gets two safety nets:
- `unhandledRejection`: log through Winston at error level and **keep running** (D-10). This deliberately overrides Node 20's default crash-on-unhandled-rejection, because the milestone goal is that the server stays up.
- `uncaughtException`: log through Winston, then `process.exit(1)` (D-11, reversible). A synchronous throw that escapes leaves unknown state, so the only change here is that the crash is now logged through Winston rather than as a raw stderr dump.

Both log only the reason's message and stack, or `String(reason)` for non-Error values, as one string. The reason object is never serialized, because an axios error would carry `DASH_API_KEY` (D-12). The handlers live in a small, testable `src/server/config/processHandlers.ts` (discretion: `app.ts` is excluded from coverage and has import-time side effects). They are registered first in `app.ts`, before the alert poll and repository init.

Purpose: ROADMAP Phase 12 success criterion 5.
Output: `processHandlers.ts` and its test, the barrel export, and the early call in `app.ts`.
</objective>

<flagged_assumptions>
The edge probe returned ERR-02 as `unclassified`. Per the spec-less fallback rules it stays **unresolved** (not auto-resolved) and is surfaced here for review. The planner's working assumptions:
1. A rejection that is handled later (Node's `rejectionHandled` event) is not tracked or retracted. Its earlier log line stands.
2. `registerProcessErrorHandlers()` is called exactly once, from `app.ts`. There is no double-registration guard, because no other caller exists.
3. For a non-Error reason, `String(reason)` is logged per D-12. A plain object therefore logs as `[object Object]`. A value with a custom `toString` that embeds a secret would be logged as-is, and no known code path rejects with such a value.
4. Winston's console transport writes the uncaught-exception line before `process.exit(1)`. This was verified through a pipe on this platform (macOS, Node 20.20.2). The same log-then-exit pattern is already used by the init-failure path.
</flagged_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Any async code path to process-level events | Rejections and exceptions can carry arbitrary objects, including axios errors holding `DASH_API_KEY`, into a process-wide log sink. |
| Process to riders | A process crash drops every live SSE stream and every in-flight request at once. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-15 | Information disclosure | `unhandledRejection` / `uncaughtException` log lines in `processHandlers.ts` | high | mitigate | `describeReason` logs only `stack ?? message` for an Error or `String(reason)` otherwise, as the single string argument to `logger.error`. The reason object is never passed as Winston metadata (D-12). The it.each test with a `super-secret-key` fixture asserts the secret never appears and that exactly one argument is passed. |
| T-12-16 | Denial of service | Process under Node 20's default unhandled-rejection crash mode | high | mitigate | The `unhandledRejection` listener logs and keeps running (D-10). The child-process check proves survival, and the unit test proves `process.exit` is not called. |
| T-12-17 | Tampering | Process state after an escaping synchronous throw | medium | mitigate | Log, then `process.exit(1)` (D-11), so the server never keeps serving from unknown state. The unit test checks log-before-exit order, and the child-process check proves exit code 1. |
| T-12-18 | Repudiation | Final log line lost if the process exits before stdout flushes | low | accept | Same log-then-exit pattern as the existing init-failure path. The child-process check shows the line is written through a pipe on this platform. |

No package installs in this plan (`tsx` is an existing devDependency, used only in verify commands).
</threat_model>
