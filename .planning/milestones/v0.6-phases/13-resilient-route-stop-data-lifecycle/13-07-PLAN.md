<objective>
Fix review WR-01, which the verifier recommended folding into gap closure because it is a new consequence of this phase's hourly refresh (SC3).

The problem:
- Before Phase 13, route/stop data never changed after boot. Now `BusDataRefreshService` swaps in a fresh dataset every hour.
- When DASH removes or renumbers a stop, every open `/predictions/stream?stop=X` loop for it keeps its 30 s interval.
- Each tick's `getPredictionsForStop` throws `NotFoundError`, which `poll()` treats as transient: it logs at error level every 30 s, forever.
- Subscribers stay connected but never receive another frame.

The fix:
- `poll()` treats `NotFoundError` as terminal for that stop. It clears the loop once, logs one warn and ends every subscriber through a new `onEnd` callback.
- The controller passes its existing single cleanup path as `onEnd`, so the response ends exactly once.
- An EventSource client then reconnects and receives the 404 that a fresh request for a removed stop already gets. Rider-facing bodies and headers do not change and there is no new SSE event type (D-13); the stream simply ends.

Purpose: DATA-01's "refreshed for as long as the server runs" must not strand live streams when a refresh changes the dataset.

Output:
- the `StreamSubscriber` subscribe API and terminal-NotFound teardown in `src/server/api/services/PredictionStreamService.ts`;
- `onEnd: cleanup` in `src/server/api/controllers/PredictionStreamController.ts`;
- the real-app E2E `src/server/api/routes/dataReloadStream.test.ts`;
- unit pins in the service and controller tests.

Design choices (Claude's discretion; all reversible, because the subscribe API has one production caller):
- **End the stream; send no farewell event.** Closing the response is enough: the standard EventSource reconnect lands on the existing 404 contract, so no body or event type changes (D-13).
- **Subscriber object instead of a third positional callback.** This follows the CLAUDE.md typed-object-param convention for multi-arg calls.
- **Warn, not error, for the teardown line.** A stop leaving the agency's dataset is an expected upstream change, logged once per stop, not once per tick.

Not in this plan:
- WR-02 (malformed-field validation) is plan 13-06, which runs in parallel on disjoint files.
- WR-03 (readiness) is deferred to Phase 14.
- WR-04 is a follow-up and is not required.
- The level of the existing transient poll-failure log is unchanged.
</objective>

<api_coverage_decision>
No external API integration: this plan changes how the server ends its own SSE streams when its route/stop dataset changes. The DASH predictions call, its URL and its client are unchanged, and no capability is added. This matches the phase's COVERAGE.md declaration.

## Flagged assumptions

- **Client reconnect:** EventSource-style clients reconnect after the server ends a stream and treat the 404 as final. Clients that do not reconnect simply see the stream end, which is still an improvement on a frozen stream. No farewell event is sent because D-13 keeps rider-facing bodies unchanged.
- **onEnd before subscribe resolves:** onEnd can only fire from a poll tick, and NotFoundError is raised synchronously at the start of getPredictionsForStop. So by the time any tick can end a stream, the controller has already stored unsubscribe. If it ever fired earlier, the controller's existing `finished` guard after subscribe still ends the response exactly once.
- **Granularity:** a stop that DASH renumbers (old id gone, new id present) is treated as removed, so its streams end. Riders reselect the new stop id; the server does no id migration.
