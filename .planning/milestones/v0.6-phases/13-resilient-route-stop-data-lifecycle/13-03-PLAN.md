<objective>
Collapse BusDataRepository's two load entry points into one atomic `load()` that either commits a complete dataset or changes nothing, and records when data last loaded and why the latest attempt failed.

- Loading makes no log calls (D-08); the background loader in plan 13-05 owns the per-attempt log line.
- A successful DASH response with zero routes is a failure (D-11).
- One malformed stop fails the whole attempt (D-12).
- Load state is one `getLoadState()` snapshot (D-14, D-16), which Phase 14 readiness serializes.
- The obsolete dedupe machinery is removed (D-19).

Purpose: DATA-02 (a failed refresh keeps the last good data) and DATA-03 (the last successful load is recorded), plus DATA-01's empty and ordering edges. This is the single load path that plan 13-05's interval loop drives.
Output: the restructured `src/server/api/repositories/BusDataRepository.ts` and its rewritten tests; `app.ts` and `upstreamTimeout.test.ts` moved to `load()`; the new real-app E2E `src/server/api/routes/dataReload.test.ts`.

Layering note: after this plan, app.ts still awaits the route/stop load before listening, exactly as today, only through `load()`. That leaves a working product. Plan 13-05 moves the load to the background (D-18).

Resolved PATTERNS discrepancies:
- Discrepancy 4: upstreamTimeout.test.ts's startup-load test called the removed boot entry point and asserted a double-prefixed error log. It is rewritten against `load()` plus `getLoadState()`. Plan 13-05 adds the loader-level log assertion.
- Discrepancy 5 (D-08 versus the repository's existing logs): all four repository log calls go. That covers the "Fetching bus data" info, the "Processed N routes and M stops" info, the "No routes found" warn and both error logs. The counts survive: `load()` resolves `{ routeCount, stopCount }`, which the loader puts in its single success line.

Prohibition probe (spec-less fallback): one bespoke prohibition kept here (no partial or empty replacement of live data). The user explicitly asked for failed refreshes to be visible rather than hidden; plan 13-05 carries that prohibition. Key leakage through `lastError` is canon (OWASP sensitive-data exposure), so it is tracked as threat T-13-08 and left to `/gsd-secure-phase` rather than minted.
</objective>
