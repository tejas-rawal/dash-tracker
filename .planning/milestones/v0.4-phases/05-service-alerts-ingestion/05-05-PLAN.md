<objective>
Close UAT gap G-05-4: booting against the LIVE DASH/Swiftly API still fails with `error: Failed to poll service alerts: DASH API returned a malformed service alerts response (body is not an object) — string body failed JSON.parse`, even after 05-03's JSON.parse string-body fallback and `entity`->`entities` rename. The user confirmed the true root cause directly from Swiftly's own API docs: the `gtfs-rt-alerts/v2` endpoint's DEFAULT response encoding is Google Protocol Buffer **binary**, not JSON — JSON is only returned when the request explicitly includes `?format=json`. `buildDashApiUrl()` (`ServiceAlertService.ts:18-21`) builds the URL with no format parameter, so axios receives raw protobuf bytes; coerced to a string, that binary payload is not valid JSON text, so `JSON.parse()` throws. This is the real root cause of both G-05-2's original report and this recurrence — 05-03's fix correctly handled JSON-*shape* assumptions but never addressed why the body wasn't JSON in the first place.

This plan: (1) appends `format=json` to the URL `buildDashApiUrl()` builds, using the same `URLSearchParams` convention `PredictionService.buildDashApiUrl()` already uses for query params, so the DASH API returns JSON instead of protobuf binary; (2) removes a stray `console.log(body)` debug statement left in `fetchFromDashApi()`'s string-body branch (a debug artifact, never intended for production, and inconsistent with this project's Winston-only logging convention); (3) keeps the `JSON.parse` string-body fallback from 05-03 — it still guards a real case (upstream serving JSON text under a non-`application/json` `Content-Type`, which skips axios's default JSON-parsing transform) even once `format=json` is explicitly requested — and documents why with a one-line comment so it isn't mistaken for dead code; and (4) adds a regression test proving `headerText`/`descriptionText`/`url` all map correctly from a fully-populated, realistic alert payload, closing UAT Test 2's field-shape check at the code level (that check could not run previously because every poll failed before reaching the mapping code).

Purpose: ALRT-01 requires a working fetch -> normalize -> filter pipeline against the REAL DASH/Swiftly API. Every prior 05-0x fix corrected how the pipeline handles the body it receives, but the pipeline still could not ingest a single real alert because it never asked the upstream for a JSON body in the first place — this plan is what finally makes the request itself correct.

Output: `ServiceAlertService.ts`'s `buildDashApiUrl()` requests JSON explicitly; the debug `console.log` is gone; the retained JSON.parse fallback carries a comment explaining why; two new tests lock in the format=json URL and the full field-shape mapping, with zero regression across the file's existing tests.
</objective>
